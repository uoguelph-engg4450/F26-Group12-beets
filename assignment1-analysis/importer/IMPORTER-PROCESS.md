# Modelling the import subsystem

We started from a class diagram generated by pyreverse and checked each importer relationship against the source code. The class names and inheritance matched the source, but several relationships that explain the import were wrong or missing:

- **Missing links to the matches.** In `beets/importer/tasks.py`, `ImportTask.candidates` and `ImportTask.match` are typed as a sequence or union of `AlbumMatch` and `TrackMatch`. Pyreverse does not resolve these types, so it drew no link from a task to its matches.
- **Over-strong library link.** `ImportSession` (`beets/importer/session.py`) only stores the `Library` passed to its constructor, and the library exists independently of the session. The link is therefore a plain association, not the aggregation pyreverse inferred.
- **No pipeline stages.** The stages in `beets/importer/stages.py` are module-level functions, so a class-based tool cannot show them.
- **Duplicate exception class.** `ImportAbortError` is defined in both `session.py` and `tasks.py`. Only the one in `session.py` is ever raised or caught.

We corrected these relationships in our own diagrams. Our first hand-made diagrams included 27 classes and every branch of the workflow. When they were scaled to a page they were unreadable, and the sequence and activity diagrams showed the same flow twice. We therefore simplified them:

- The class diagram keeps the 16 classes needed to explain an import, with two to four key operations each and no parameter lists. Implementation classes such as `ImportState`, `Distance` and the archive tasks are left out.
- The activity diagram shows the pipeline at the level of stages, in four swimlanes. Rarer branches (rescan, merge, upgrade and resume) are left out; the figure shows only normal matching, import as-is and skip.
- The sequence diagram zooms in on a single interaction, metadata lookup and choice, so that it does not repeat the activity diagram. It is placed in the appendix to keep the subsystem section within two pages.

Two choices of notation needed care. Module functions such as `tag_album` were shown as a participant labelled "(module)" rather than as an invented class. Events were drawn as ordinary actions and synchronous messages rather than UML signals, because Beets delivers them synchronously and uses their return values.
